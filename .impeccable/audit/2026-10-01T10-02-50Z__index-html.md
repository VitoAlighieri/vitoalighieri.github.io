# Impeccable audit: bielmartinez.com (index.html, web)

**How this was tested.** I measured everything in Chrome 141 headless, driven by Puppeteer, with WebGL running on SwiftShader (software rendering).
- **Viewports:** desktop at 1440×900, phones at 393×852 and 320×640 with `isMobile` and `hasTouch` on, landscape at 844×390 and 667×375. A 200% browser zoom was simulated as a 720×450 viewport at 2× pixel density.
- **Touch:** gestures were sent as raw CDP touch events (`Input.dispatchTouchEvent`). Chrome's synthesized scroll gesture had no effect in this environment, so I didn't rely on it.
- **Contrast:** checked two ways. First by formula on the token pairs. Then on the real page: I hid all text, screenshotted, and compared each text colour against the actual pixels behind it, over 6 frames because the trace moves.
- **Performance:** run with CPU throttled 4×. The phone load test also used slow-4G (1.6 Mbps, 150 ms) through a gzip server in the scratchpad, to match GitHub Pages compression.
- **Read-only:** no project file was changed (`git status` is clean). Scripts and screenshots are in `/tmp/claude-0/-home-user-vitoalighieri-github-io/2af46462-be10-5893-b085-bc4d068a26e3/scratchpad/review-audit/`.

## Implementation Integrity verdict: pass

The design hangs together as one product-specific system, "The Handheld Receiver".
- **Live values are real.** The strip readout (f/A), the trace captions and the section codes are all generated from the same `data-*` attributes that drive the scope (`app.js:440-462`). The years-of-experience figure is computed (`app.js:465-469`).
- **Tokens match exactly.** All 15 colours in DESIGN.md are CSS variables with identical values (`styles.css:2-27`).
- **The detector findings are mostly intentional.** I checked all 87 in context:
  - *By design, documented in DESIGN.md:* `dark-glow` ×11 (the "lit means live" glow), `gpt-thin-border-wide-shadow` ×6 (the dock shadow and the long soft shadow under work cards), `repeating-stripes-gradient` (the tick scales), `all-caps-body`, `wide-tracking` and `tiny-text` ×2 each (the mono role labels on phones), and `pulsing-dot`.
  - *False positives:* `cramped-padding` ×9 (these are hairline rules sitting above lists and padded sections) and `design-system-font` (JetBrains Mono *is* declared in DESIGN.md).
  - *Real:*
    - `skipped-heading`
    - `design-system-radius` (6 px)
    - `undersized-ui-text` ×47 (the 10.56 px label size is used on controls)
    - `marquee` ×2 (infinite decorative loops)
    - `em-dash-overuse` (copy only)

There are two kinds of drift. First, layers of CSS stacked on top of old rules, leaving dead declarations. Second, docs and on-page claims that the build doesn't keep: "honours reduced motion", "keyboard focus is always visible", "stable under text zoom", and a README that describes a different repository.

## Executive summary

- **Score:** 12/20, Acceptable.
- **Issue count:** P0: 0 · P1: 5 · P2: 13 · P3: 10.
- **Top issues:**
  1. Keyboard focus is invisible on the undocked strip, on desktop and phone.
  2. On phones, focused controls sit behind the dock or the strip.
  3. The hero's copy and call-to-action ("Open a channel") only appear once three.js, GSAP and app.js have loaded and the intro has run.
  4. The phone layout breaks at 150% text size or more (an owner requirement in PRODUCT.md).
  5. The trace moves forever, with no way to pause it, and reduced-motion only slows it to half speed.
- **Next steps:** fix keyboard focus (harden), stop gating the hero copy on JS (optimize), make the phone layer survive text scaling (adapt). Then the contrast and token clean-up.

## Detailed findings

### P1: Major

**[P1] The hidden docked strip takes keyboard focus first**
- **Location:** `assets/css/i18n.css:9-10` only turns off `pointer-events`. The strip is hidden with `opacity:0` in `assets/css/styles.css:135-138`, and the visibility switch is in `app.js:585-589` and `i18n.js:292-305`.
- **Category:** Accessibility.
- **Impact:** At the top of the page, Tab stops 1–4 on desktop ("BMJ.", EN, ES, "OPEN CHANNEL") and 1–3 on phone land on elements whose combined opacity is 0. Each one sits at the top of the hero, under the "Signal — Active" label. The focus ring is drawn but can't be seen, and a keyboard user can switch the language without seeing what they pressed. Verified with `keyboard.js`.
- **WCAG:** 2.4.7 Focus Visible (AA), 2.4.11 Focus Not Obscured (AA).
- **Recommendation:** Keep the strip out of the tab order and the accessibility tree until it docks: apply `inert` to `#topbar` (or `visibility:hidden`) while it isn't docked, and remove it when docked. Let one module own that docked state.
- **Command:** /impeccable harden

**[P1] On phones, focused controls hide behind the dock and the strip**
- **Location:** The dock is fixed in `assets/css/mobile.css:41-48`. `html` has no `scroll-padding` (`styles.css:31`). Only `.section` has `scroll-margin-top` (`styles.css:103`).
- **Category:** Accessibility.
- **Impact:** Measured at 393×852:
  - Tabbing to the second "Show detail" button leaves 72.5% of it under the dock.
  - "↑ Top" in the footer ends up 100% under the dock (`obscure-17.png`).
  - With Shift+Tab, "Show detail" ends up 99% under the 60 px strip.
- **WCAG:** 2.4.11 Focus Not Obscured (Minimum, AA).
- **Recommendation:** On phones, add to `html`: `scroll-padding-top: calc(var(--bar) + env(safe-area-inset-top) + 8px); scroll-padding-bottom: calc(var(--dock-room) + 8px)`. Optionally also hide the dock while focus is in the footer.
- **Command:** /impeccable harden

**[P1] The hero copy and call-to-action wait for about 1 MB of JS before they appear**
- **Location:** The inline `js` class (`index.html:14`). The CSS rules that hide the hero (`styles.css:474-481`). Seven scripts loaded without `defer` (`index.html:486-495`). The 2.6 s safety fallback sits inside app.js (`app.js:42`), so it can't run until three.js has loaded.
- **Category:** Performance.
- **Impact:**
  - **Phone, slow-4G, 4× CPU, gzip on:** first paint at 1.32 s, but the largest content paint (the lede and the call-to-action) is at **4.42 s**. The DOMContentLoaded event fires at 4.08 s. Long tasks reach 607 ms, 401 ms and 399 ms.
  - **Same test without compression:** largest content paint at 8.44 s.
  - **Desktop, 4× CPU:** largest content paint at 3.03 s.
- **Recommendation:** Render the hero copy visible with CSS only, and let the intro animate *from* the visible state. Load scripts with `defer`, and put the fallback timer in the inline head script. Preload the Anybody display font.
- **Command:** /impeccable optimize

**[P1] Phone layout breaks at 150% text size or more**
- **Location:** Text that can't wrap: `.readout` (`styles.css:543`) and `.sys-head .when` (`styles.css:338`). Body text sized in px, which doesn't follow the user's font setting: `body` (`styles.css:35`) and the phone lede at 15 px (`mobile.css:189`). Phone chrome built in whole pixels (`i18n.css:89-97`, `mobile.css:146`). The only `overflow-x` guard is on `body`.
- **Category:** Responsive / Accessibility.
- **Impact:** Tested by setting Chrome's default font size with `Page.setFontSizes`.
  - At 125%, layout holds.
  - At 150%, the phone's layout viewport widens to 446 px. At 175% it reaches 516 px, at 200% 585 px.
  - The lede, the "Exp" readout and the call-to-action are cut off at the right (`textscale-150-393.png`).
  - At 200%, "SIGNAL — ACTIVE" overlaps the language pill.
  - The lede stays at 15 px while the text around it grows.
  - PRODUCT.md's owner requirement ("stable under … text zoom") is not met.
- **WCAG:** 1.4.4 Resize Text, related; PRODUCT.md owner requirement.
- **Recommendation:** Let these strings wrap at narrow widths (or use `min()` widths with ellipsis). Size the lede and body text in rem. Add `overflow-x: clip` on `html`. Retest at 150% and 200%.
- **Command:** /impeccable adapt

**[P1] The trace never stops moving, and reduced-motion doesn't stop it**
- **Location:** `app.js:14` (reduced-motion only sets speed to 0.5), `app.js:246-288` and `app.js:350-392`.
- **Category:** Accessibility.
- **Impact:** With reduced-motion emulated, the hero WebGL frames keep changing, and so does the docked strip trace on desktop and phone. The strip is fixed, so moving content sits next to every section of the page with no pause control. The colophon's "Honours reduced motion" overstates this.
- **WCAG:** 2.2.2 Pause, Stop, Hide (Level A).
- **Recommendation:** Under reduced-motion, render one still frame, and re-render only on retune or touch. Also add a small pause/resume control on the strip, or pause the strip trace after a short idle period.
- **Command:** /impeccable animate

## What was exercised, and what stayed untested

**Exercised with raw touch:**
- **Hero tap:** fires a wave packet and a tap ring.
- **Sideways hero drag:** stretches the trace up to the ×3.2 cap, shows the probe readout, springs back on release, and doesn't scroll the page.
- **Vertical drag on the hero:** scrolls the page (0 → 385 px) without touching the trace.
- **Deck swipe:** snaps to card 2 and updates the pager, the dock (CH·02) and the strip ("CH·02 — BREAK").
- **Mostly-vertical drag on the deck:** scrolls the page instead of the deck.
- **Dock tap:** opens the index with focus on the current row.
- **Tapping "02 BREAK" in the index:** scrolls the deck to that card and retunes the page.

**Keyboard and reduced motion:** the index dialog moves focus in, traps Tab, closes on Esc and returns focus to the dock button. Picking a row by keyboard moves focus to that section's heading. Under emulated reduced motion, the reveals, the accordion (label and +/− state), the dialog, the language chip and the pager all still change visibly.

**Untested:**
- Real iOS Safari: `touch-action:pan-y` with pointer capture, View Transitions, `text-box` trimming, `svh` units, the back-swipe while the index is open.
- Real Android: system text scaling, and momentum fling. Headless Chrome produced no momentum, so the dock's duck-on-fling stayed unverified.
- Frame timing on a real GPU (SwiftShader inflates GPU cost).
- Screen readers: only the accessibility tree was inspected.
- Real Windows High Contrast (only Chromium's emulation was used).
- Firefox's text-only zoom.
- Pinch-zoom of the visual viewport.

## Patterns and systemic issues

- **Hidden-but-focusable chrome, and fixed chrome with no scroll padding.** The strip and dock overlays were built for pointer and touch input; keyboard focus wasn't modelled. Both P1 focus issues come from this.
- **New CSS stacked on old.** The append-in-order blocks (T1-01…T2-06, then mobile.css) override earlier rules instead of replacing them. This produces the dead CSS, the duplicate +/− systems and the misleading "deleted above" comments.
- **Transparencies are typed in, not tokenized.** The base palette is fully tokenized, but every transparency (tint, wash, glass, glow steps) is a hand-typed `rgba`, in 28 different amber opacities.
- **Whole-pixel geometry fights text scaling.** The phone's pixel-exact pills, chips and px-sized text stay fixed while the rem-sized labels around them grow. Lines that can't wrap then push the layout wider than the screen.
- **Motion promises run ahead of the behaviour.** Product, README and colophon claims about reduced motion are stronger than what the code does.

## Positive findings

- **Phone index dialog:** a properly built modal with `aria-modal`, `inert` plus `aria-hidden` on the background, a focus trap, Esc, focus returned on close, focus moved to the destination heading, the Android back gesture, and history integration.
- **Overflow:** none at 320, 360, 390, 414, 600, 720, 768, 1024 and 1440 px, or in landscape, in EN or ES.
- **Touch targets:** every phone control's real hit area is 44 px or more, including the `::before` extensions (EN/ES 46×46, ↑ Top 76×48). The COPY key measured 68×43, effectively 44.
- **Reduced motion:** reveals, headline wipes, the dock, the index and the accordion all keep their state changes as instant moves or fades.
- **Without JavaScript:** nothing is hidden, the details are open, and the phone-only chrome stays hidden.
- **Performance basics done well:**
  - Pixel density is capped.
  - The 3D scene only renders while the hero is on screen.
  - The mini traces run at 30 fps and only while visible.
  - The index traces run only while it's open.
  - There's no backdrop blur over WebGL on touch devices.
  - Desktop scrolling at 4× CPU: p50 16.7 ms, p90 16.8 ms.
